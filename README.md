# dp1c — a DP-1 preservation capsule that proves itself

Prototype, 2026-10-30. Two Python files and an engine builder. Builds `*.dp1c` capsules per DP-1 v1.1.0 §9 and fills what the spec leaves blank: the engine layer (`/meta/engine/<layer>`, with a content-addressed `imageRef`) and the `repro.frameHash` in §5, computed by a harness that drives Chromium over the DevTools protocol inside a pinned engine image, with the network namespace unshared, the clock and the frame clock pinned and the viewport set before navigation. Two inputs: a directory of files, or a capture the FF1 already made of a work it played (FF OS's offline-artworks store), which the capsule then replays. The proposed spec text, how this fits the device, and the decisions it leaves to the team are in `SPEC-PROPOSAL.md`.

Reviewed read-only by Codex (gpt-6-astra) and Grok on 2026-10-30, twice, both "revise" both times; this version answers the blockers from both passes (see "What changed after review").

## The claim it lets an owner test

A capsule is a file. Anyone with the file, the engine image it names, and a Linux machine with bubblewrap can run `verify` offline, with no Feral File service anywhere, and get a yes or a no: the work's files are exactly what the publisher packed, and the work rendered to the same pixels the publisher recorded, inside the same engine. Without the image, `--host` compares against this machine's Chromium instead; that result is reported as a different-engine comparison, never as `reproduced`.

## What it does

```
engine/build-engine.sh 2026/10/20 out/ [exact-chromium-pkg-url]        # once per engine: content-addressed rootfs + manifest
python3 dp1c.py build  WORKDIR --engine out/engine-<sha>.tar.zst --out work.dp1c [--entry index.html] [--title ..] [--source URL] [--provenance p.json] [--seed 0x..] [--created ISO] [--frames 60] [--pin-random SEED]
python3 dp1c.py import-capture --cache-root ~/.cache/offline-artworks --source <item.source URL> --engine out/engine-<sha>.tar.zst --out work.dp1c   # from an FF1's offline store
tools/ff1-cast.py <ff-cli device name> downloadPlaylistItem '{"item": {...}}'   # ask an FF1 to capture a work first; then pull its ~/.cache/offline-artworks over SSH
python3 dp1c.py verify work.dp1c [--engine out/engine-<sha>.tar.zst] [--host] [--allow-engine-mismatch] [--png out.png]
python3 dp1c.py info   work.dp1c
python3 dp1c.py keygen key.pem && python3 dp1c.py sign work.dp1c --key key.pem --role publisher
./verify-in-docker.sh out/engine-<sha>.tar.zst work.dp1c [work.dp1c.sig.json] [--require-signer did:key:...]   # Docker instead of bubblewrap (measured on an Apple Silicon Mac, below)
```

`build` copies the work into `assets/`, hashes every file, renders once inside the engine, refuses to write a capsule if any resource failed to load, any HTTP error other than favicon occurred, or an uncaught exception fired (`--allow-render-errors` records them instead), writes the pin, the reference frame and its hash, and packs a deterministic archive whose sha256 is the capsule id. Same inputs and the same `--created` give the same bytes.

`import-capture` reads the record FF OS wrote when the device ran the work (`items/<sha256(source)>.json`: entry URL, every request with status, declared content type, replayable headers, redirect target and body hash) and the blobs it names, copies the blobs into `assets/<sha256>`, writes the table to `meta/capture/resources.json`, carries the DP-1 item verbatim (title, provenance, license), and renders with request interception on: the page navigates to its real URL and every request is answered from the table, the way the device's own offline replay does. Nothing is fetched; a request the table cannot answer fails with `net::ERR_FAILED`, is recorded, and the build refuses. Only the headers that change how the browser treats a response are replayed (the CORS and cross-origin set FF OS allowlists, plus the declared content type). `verify` replays the same way, after static checks that every body digest names exactly the asset it says, every asset is referenced, and every redirect is a 3xx to an http(s) URL (prototype limits, refused at import: GET and HEAD only, one record per method+URL, bodies under 200 MB).

`sign` writes a detached Ed25519 signature over the capsule id into `<capsule>.sig.json`, in the DP-1 §7 object shape with a `did:key` identifier (`keygen` makes a key). `verify --require-signer <did:key>` refuses a capsule not validly signed by that key; forged signatures and signatures carried over to a tampered capsule both fail.

Signatures are checked with the `cryptography` library when it is present and with an RFC 8032 implementation in plain Python when it is not (the engine image built on 2026-10-30 has no library; the builder lists `python-cryptography` for the next one). The result says which (`checkedWith`), and the tests check the example sidecar both ways, plus a flipped character.

`verify` checks three things and reports them separately: every file under `assets/` matches the manifest and the playlist (no missing, no extra, no changed); the three copies of the reference frame agree (playlist, `reference.json`, the PNG's own pixels); and a fresh render inside the pinned engine, under the pinned harness, reproduces the frame hash. Verdicts: `reproduced` (exit 0), `reproducedOnDifferentEngine`, `nearOnDifferentEngine`, `reproMismatch`, `renderProblems` (something failed to load, threw, was still in flight, ran in a worker or out-of-process frame, or in replay was not served from the capture; the pixel comparison is reported but does not decide, and a capsule that recorded problems at build is reported this way every time), `assetsCorrupt` (a file or a static check failed; nothing is rendered), `unsigned`, `signatureInvalid` (all exit 2). Flags, environment and value ranges for the render come from this tool, never from the capsule.

### The engine image

`engine/build-engine.sh` builds a root filesystem from the Arch Linux package archive at a dated snapshot, optionally with one exact Chromium package installed over it, with no root and no daemon (pacman inside `unshare -r`). It holds Chromium, the fonts FF OS ships (DejaVu, Liberation, Noto CJK) plus whatever GTK pulls in (Adwaita), Python with Pillow and zstandard, and util-linux for `setpriv`. Package install scriptlets do run; afterwards the machine id is emptied and install dates are stripped from the package database. The tree is packed as a deterministic tar (sorted, mtime 0, numeric owner 0) and single-threaded zstd 19 with no checksum frame; the sha256 of that file is the engine id. The sidecar `engine-<sha>.json` records every package version, the sha256 of every package file, the archive URL, the exact Chromium package URL and the host build tools. About 575 MB compressed, 1.7 GB unpacked; one image serves every capsule built with it.

### The sandbox

Both build and verify run `harness.py` under bubblewrap: every namespace unshared; the image read-only at `/` (or, with `--host`, this machine's root filesystem); `assets/` read-only at `/work`; one fresh directory writable at `/out`; the harness read-only at `/harness`; environment cleared and set to the pin's `env`; cwd `/`. The harness brings loopback up inside the empty network namespace (a Python ioctl, needs CAP_NET_ADMIN), then starts Chromium through `setpriv` with the bounding set emptied and no-new-privs set, so the browser runs with no capabilities at all. Measured: `CapEff 0`, `CapBnd 0` in the browser process. A work that needs a host outside `assets/` fails with `net::ERR_INTERNET_DISCONNECTED` from the kernel, and build refuses.

The harness talks to Chromium over the DevTools pipe: device metrics set before navigation (the page sees the pinned viewport from its first frame), timezone and locale overrides, cache disabled, virtual time paused at a fixed epoch before navigation, a settle budget that advances only while no fetches are pending, then the frame schedule, then the screenshot. The frame schedule exists because headless Chromium's compositor drives `requestAnimationFrame` on wall-clock time: on a work whose title fade counts frames, two renders in the same image differed by a few frames of fade. So the engine hands the page its own frame clock: `requestAnimationFrame` is replaced before any script runs by a queue the harness ticks, exactly `frames` times (default 60) at `frameIntervalMs` (default 16.667) of virtual time each, in the top document and every same-process iframe, then frozen; the tick is guarded by a per-run nonce the page cannot see. The page's `Date.now()`, timers and `performance.now()` all follow virtual time; `navigator.hardwareConcurrency` is pinned. The timestamp each callback receives is the frame's virtual time, computed by the harness as the settle budget plus one interval per frame, not read from `performance.now()`, which under virtual time carries sub-millisecond jitter (10983.3 against 10983.4 on two builds of the same page) that would otherwise reach the work. In the files layout the loopback origin is pinned too (`loopbackPort`), so two builds record the same `href`. Not under this clock: workers and out-of-process iframes (detected through target auto-attach and reported as a render problem, so the build refuses and verify says `renderProblems`), and CSS animations and video, which are not detected (`SPEC-PROPOSAL.md`, decision 4). Measured: a page that starts a worker is refused at build naming the worker. Measured on test pages in host mode, two builds each: a rAF counter shows frame 60 at 10,983 ms of virtual time; a 100 ms interval timer shows tick 110 at 11,000 ms; a same-process iframe and its parent both reach frame 60; a callback cancelled by an earlier callback in the same frame does not run; a page that assigns to `requestAnimationFrame` or calls the tick with a guessed nonce gets a TypeError and a refusal. All identical across builds. `Math.random` and `crypto.getRandomValues` are left alone by default, because on-chain generative art seeds itself from the token hash (§5 requires the seed logic to live in the payload). For a work that does not, `build --pin-random <seed>` has the harness install a seeded generator before any page script runs; the work is untouched, the seed is recorded in the pin, and the capsule then certifies one witnessed run of the system. Measured: a test page drawing from `Math.random` gave different frames on two unpinned builds and identical frames and capsule ids on two pinned ones.

## Worked example 1: Fidenza #503 (files)

`examples/fidenza-503.dp1c`. HTML read straight from the Art Blocks on-chain generator (`getTokenHtml`, block 26308641), p5 1.0.0 inlined by the contract, zero network references. 1920×1080, 10 s settle, 60 frames. Measured on this machine:

- Same inputs, two builds: same capsule id.
- Inside the pinned engine, verify: `reproduced`, exit 0.
- Host Chromium 155 (same version, different build and environment) via `--host` with the image hidden: same frame hash, reported as `reproducedOnDifferentEngine`, exit 2.
- Chromium 154 image via `--allow-engine-mismatch`: same frame hash, reported as `reproducedOnDifferentEngine`. One version step, zero pixel drift, for this work.
- Tampers caught: one nibble of the token hash (assets and pixels both fail); a comment-only edit (pixels same, assets fail); an extra unlisted file; an edited `reference.json` frame record. Wrong engine image refused. Missing engine refused without `--host`.
- A test page loading p5 from a CDN is refused at build with the kernel's disconnected error.
- **Different machine:** a Mac mini (Apple Silicon, macOS 26.5), Docker in a Colima VM with Rosetta running the x86-64 image, network none, read-only root: `reproduced`, same frame hash, exit 0. Verify took about six seconds once the image was imported.

## Worked example 2: E-volved Formula #22 #1 (replay, captured by an FF1)

`examples/evolved-formula-22-1.dp1c`, built from `examples/evolved-formula-22-1/capture/`, which is the record and blobs copied unchanged from the Kitchen FF1's offline store (feral-controld 2.0.11, Chromium 150) after one `downloadPlaylistItem` for a work in the Feral File feed: a WebGL piece of seven requests (HTML, CSS, two modules, two shaders, a 404 favicon), 22 KB. Measured:

- Import and render inside the pinned engine: all seven requests answered from the table, no misses, no fetches.
- Before the frame schedule: two renders in the same image gave different frame hashes (the title fade had run a different number of frames). With it: `reproduced`, exit 0, and two builds give the same capsule id.
- Tampers caught before any render, all `assetsCorrupt`: one bit flipped in a shader blob; one resource removed from the table (its blob is then unreferenced); a resource whose digest is a filesystem path; two blobs swapped with a truthful manifest (names no longer equal digests); an entry changed to `about:blank`.
- The device marked the capture `partial` because of the favicon 404; the importer requires `--allow-incomplete` for that, and the render treats a favicon 404 as nothing.
- **Different machine:** the same Mac mini, same image under Rosetta: `reproduced`, same frame hash, all seven requests replayed.

## What changed after review

Codex and Grok each found the same five blockers in the first version and a long tail. Fixed here: verify checked only a screenshot's existence (now the harness's exit, both output files, and the frame geometry are required, and output goes to a fresh directory outside the capsule); the asset check covered only listed files (now the whole tree, both directions, and the playlist's list); the engine pin was bypassed by cached or directory engines (now the computed digest is the only thing trusted, cache entries carry a completion stamp, and a mismatch refuses unless explicitly allowed and is then reported as a different engine); capsule fields reached `bash -c` (now the harness reads a JSON config on stdin and the entry is URL-encoded); the host path only blocked DNS (now it runs under bubblewrap with the network namespace unshared too); a missing dependency rendered a blank frame as success (now load failures fail the build); the pixel hash ignored geometry (now width, height and format are in the hash); the engine id depended on multithreaded zstd and install-time state (now single-threaded, machine id and install dates normalized); the viewport and clock were not pinned (now set over DevTools before navigation); the harness copy in the image was not the one that ran (now the harness that runs is bind-mounted and its sha256 is in the pin).

Second pass (Codex and Grok, same day, on the replay layout and the frame schedule). Fixed: a resource digest reached the filesystem unvalidated and the asset check only tested membership (now digests must be 64 hex and name exactly `assets/<digest>`, every asset must be referenced, and no render happens if any static check fails); `verify` ignored render problems when the pixels matched, and did not require the entry to come from the capture (now `renderProblems` outranks the pixel comparison, and replay requires the entry served from the table and the page landed on a captured URL); the over-64 MB loopback fallback was intercepted by the same filter and changed response semantics (removed; bodies over 200 MB are refused at import); the protocol loop could lose a budget-expiry event that arrived mid-command and recursed once per paused request (now waiters are registered before the command and events are delivered without re-entry); the frame clock ticked only the top document, could be ticked or unfrozen by the page, swallowed callback exceptions, and ran cancelled callbacks (now every same-process document is ticked, the tick needs a per-run nonce, exceptions are render problems, cancellations are honoured); interception and diagnostics stopped before the screenshot (now they run through it); `status: 0` became 200 and headers could be duplicated (now a missing status fails the request, headers are deduplicated and limited to an allowlist, and a redirect record must be a 3xx to an http(s) URL); a request paused in the last frame could go unanswered (now the harness drains the pipe before the capture and anything still in flight is a render problem); workers and out-of-process frames were invisible (now detected and reported); a capsule built with recorded problems could verify as `reproduced` by matching its own error pixels (now never exit 0); the engine manifest recorded the last package's digest as the image digest (builder fixed, manifest corrected); the Docker launcher reused a tag without checking it (now labelled with the digest and checked); verify imported the signature library even without a sidecar, which the image lacks (now imported only when a sidecar is present).

## Tests

`python3 tests/run.py` (host mode, about ten seconds) re-measures the frame-clock claims on the five pages in `tests/pages/`: two builds of each page give identical bytes; 60 ticks are delivered and the expected callbacks run (one per frame; none on a timer-only page; 120 across a parent and its same-process iframe; one where the first callback cancels the second); `Date.now()` at capture is the epoch plus the settle budget plus 60 intervals; the worker page is refused naming the worker; a capsule with one byte of its entry changed is `assetsCorrupt` before any render; a host-built capsule verifies exact as `reproducedUnpinned`, exit 2; the example signature is valid with and without the library and invalid with one character flipped. Its first run found the two defects the paragraph above now guards against (the jittering callback timestamp and the random, recorded loopback port). The reference record carries what the clock did (`frameClock`: ticks, callbacks, documents), so a verifier can see it without a screenshot.

## What is real and what is not

Real: both layouts, the deterministic archive, the pinned engine image and its builder, the kernel-level offline render inside it with capabilities dropped, the DevTools-driven capture with pinned clock, frame clock and viewport, replay of a device capture with request interception, the three-way asset and frame checks, exact reproduction across runs and across one Chromium version step, the refusals.

Not yet real, in order of how much they matter:

1. **Cross-machine reproduction beyond one pair.** Measured once: this x86-64 laptop under bubblewrap and an Apple Silicon Mac mini running the image under Rosetta in Docker give the same hash for both examples. SwiftShader and Skia may still take CPU-specific paths on other hardware; the claim to widen: more machines, including an FF1 and a real x86-64 Docker host.
2. **Bit-exact engine rebuild.** Install scriptlets run during the build and generate caches. The manifest now carries every package file's sha256, so a rebuild can be checked against the image digest, but a matching rebuild has not yet been demonstrated. The blob on IPFS plus Arweave is the real pin; the recipe is the fallback.
3. **The engine in 2036.** The image runs under bubblewrap today and would import as an OCI container. Running it under x86-64 emulation, with a pinned kernel and CPU model, is the long-term path and has not been exercised.
4. **Who signs.** The example is signed by a prototype key generated on this laptop. Which key signs in production and where its `did:key` is published is open.
5. **On the device.** The capture is the device's and the import is a laptop command. Capture-to-capsule and the verify loop inside feral-controld are specified in `SPEC-PROPOSAL.md` ("How this fits the device") and not built.
6. **Which frame, and tolerance.** Frame 60 is a default, not the artist's statement; CSS animations and video run on compositor time and are not yet under the frame clock. Decisions 4 and 5.

## Why this and not a screenshot

A screenshot proves what the publisher saw. A capsule lets the owner re-derive it, inside the same engine, with nothing else reachable. The difference is what has to be trusted: the file and the image, not the publisher.
